# DollarSpot Sentinel v5.2 - Specifica hardening tecnico

## Stato attuale osservato

Il progetto ha gia una logica agronomica solida e una pagina superintendent evoluta. I punti deboli principali sono nel collegamento tra frontend, Apps Script e Google Sheets.

Criticita viste nel codice condiviso:

- `doPost` non verifica un token.
- Il campo viene inviato dal form HTML e quindi puo essere modificato.
- Il frontend usa `fetch(..., mode: 'no-cors')`, quindi non conosce l'esito reale del salvataggio.
- La pagina salva `rullatura`, ma il backend v5.1 non la gestisce esplicitamente in `doPost`.
- Date future possono essere interpretate come trattamenti attivi.
- Il modello calcolato nella pagina non e perfettamente allineato al modello backend v5.1/v5.2.
- Chiavi sensibili sono hardcoded nel codice.

## Modifiche v5.2 obbligatorie

### 1. Token per campo

Aggiungere al foglio `Campi` colonne dedicate:

| Campo | Scopo |
| --- | --- |
| `campoId` | Identificativo stabile, non modificabile dall'utente |
| `tokenCampo` | Token segreto specifico del campo |
| `attivo` | Abilita/disabilita campo |
| `ultimaRotazioneToken` | Data rotazione token |

Regola: il backend deve ricavare `nomeCampo` da `tokenCampo`, non dal payload HTML.

### 2. Autenticazione `doPost`

Ogni POST deve includere:

```json
{
  "tokenCampo": "...",
  "tipo": "azoto",
  "payload": {}
}
```

Flusso backend:

1. Legge `tokenCampo`.
2. Cerca campo attivo in `Campi`.
3. Se non valido, rifiuta.
4. Imposta internamente `data.campo = campo.nomeCampo`.
5. Continua con la validazione del tipo.

### 3. Tipi supportati

`doPost` deve accettare solo:

- `azoto`
- `ferro`
- `fungo`
- `rullatura`
- `annotazione`
- `feltro`
- `domande`
- `config_completa`

Ogni altro tipo va scritto in `Errori`/`Audit` e respinto.

### 4. Validazione dati

Per tutti i tipi:

- `data` obbligatoria dove serve.
- No date future.
- No date invalide.
- `kg` numerico e positivo per azoto/ferro.
- `npkPct` tra 0 e 100.
- `prodotto` fungicida in lista ammessa.
- `evento` in lista ammessa.
- `campo` non accettato dal client come fonte autoritativa.

### 5. Risposta JSON reale

Obiettivo: sostituire `mode: 'no-cors'` con una risposta leggibile.

Risposta successo:

```json
{
  "status": "ok",
  "tipo": "azoto",
  "campoId": "green-01",
  "savedAt": "2026-05-11T..."
}
```

Risposta errore:

```json
{
  "status": "error",
  "code": "INVALID_TOKEN",
  "msg": "Token campo non valido"
}
```

Se CORS resta un limite di Apps Script, la pagina deve almeno mostrare "inviato, verifica in corso" e non "sincronizzato" certo.

### 6. Audit e log errori

Creare o usare foglio `Audit`:

| Timestamp | CampoId | Campo | Tipo | Esito | Messaggio | PayloadHash |
| --- | --- | --- | --- | --- | --- | --- |

Creare o usare foglio `Errori`:

| Timestamp | Gravita | Funzione | Campo | Errore | Dettaglio |
| --- | --- | --- | --- | --- | --- |

### 7. Meteo robusto

Requisiti:

- WeatherAPI principale se disponibile.
- Open-Meteo fallback.
- Cache giornaliera.
- Ultimo dato valido se entrambe le API falliscono.
- Log chiaro quando si usa fallback/cache.
- Soil temperature da Open-Meteo anche se WeatherAPI e la fonte principale.

### 8. Allineamento modello frontend/backend

Per evitare risultati diversi:

- Il rischio ufficiale deve essere calcolato dal backend.
- La pagina puo mostrare una preview locale, ma deve indicarla come "stima locale".
- La pagina deve poter richiedere al backend `analizza_campo` per ottenere il rischio ufficiale.

Differenze da risolvere:

- Cultivar.
- Temperatura suolo.
- Finestra stagionale.
- Soglia climatica adattiva.
- Cache profilo climatico.

### 9. Email feedback

Il bottone email non deve registrare subito `macchie_viste`.

Flusso consigliato:

1. Click email.
2. Pagina conferma.
3. Pulsanti:
   - `macchie_viste`
   - `nessuna_macchia`
   - `trattato`
   - `situazione_dubbia`
4. Solo al secondo click si scrive in `Storico`.

## Modifiche frontend minime

### Payload

Sostituire:

```javascript
const payload = {...data, tipo, campo: document.getElementById('fieldName').value};
```

con:

```javascript
const payload = {
  tokenCampo: getTokenCampoFromUrl(),
  tipo,
  data
};
```

Il campo visualizzato puo restare in pagina, ma deve essere readonly e valorizzato dal backend o da configurazione firmata.

### Date future

Aggiungere prima di ogni salvataggio:

```javascript
function isFutureDate(value) {
  if (!value) return false;
  var input = new Date(value + 'T00:00:00');
  var today = new Date();
  today.setHours(0, 0, 0, 0);
  return input.getTime() > today.getTime();
}
```

### Sincronizzazione

Non mostrare `Sincronizzato` se il browser non riceve una risposta verificabile.

## Priorita implementazione

3. Validazione date e payload.
4. Audit/Errori.
5. Meteo fallback/cache/soil temperature.
6. Rischio ufficiale backend.
