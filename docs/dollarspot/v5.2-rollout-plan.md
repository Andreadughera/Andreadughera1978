# DollarSpot Sentinel v5.2 - Piano di rilascio senza disservizio

## Obiettivo

Portare DollarSpot Sentinel dalla versione in test sui campi reali a una versione v5.2 piu sicura, stabile e pronta per un uso commerciale, evitando disservizi ai superintendent attualmente coinvolti.

## Principio guida

La versione oggi usata dai campi resta invariata finche la v5.2 non e stata verificata in parallelo.

Non cambiare:

- URL della Web App attuale.
- Spreadsheet in uso ai 7 campi.
- Pagina HTML attualmente distribuita.
- Trigger giornalieri in produzione.
- Struttura dei fogli di produzione.

## Ambienti

### 1. Produzione corrente

Nome suggerito: `DollarSpot Sentinel v5.1 PRODUZIONE`

Uso:

- Continua a inviare email reali.
- Continua a ricevere registrazioni dai superintendent.
- Resta il riferimento operativo finche la v5.2 non e promossa.

### 2. Test interno

Nome suggerito: `DollarSpot Sentinel v5.2 TEST`

Uso:

- Copia del codice Apps Script.
- Copia dello spreadsheet o fogli dedicati `*_TEST`.
- Nuovo URL Web App.
- Nessun superintendent coinvolto.
- Email inviate solo all'agronomo.

### 3. Pilota controllato

Nome suggerito: `DollarSpot Sentinel v5.2 PILOTA`

Uso:

- Un solo campo fidato.
- Vecchia versione ancora disponibile come rollback.
- Monitoraggio manuale dei primi salvataggi e alert.

## Fasi operative

### Fase 0 - Backup

Prima di qualunque modifica:

1. Duplicare lo spreadsheet di produzione.
2. Esportare o copiare il codice Apps Script attuale.
3. Annotare URL Web App, trigger attivi e proprieta script.
4. Salvare una copia della pagina HTML attuale.

### Fase 1 - Hardening in v5.2 TEST

Implementare le modifiche v5.2 solo nell'ambiente test:

- Token per campo.
- Controllo token anche in `doPost`.
- Campo ricavato dal token, non dal form HTML.
- Supporto backend per `rullatura`.
- Validazione date non future.
- Validazione payload per tipo.
- Log errori e audit.
- Cache meteo/fallback piu robusti.
- Allineamento rischio frontend/backend.

### Fase 2 - Modalita ombra

La v5.2 calcola gli stessi campi della produzione, ma:

- Non invia email ai superintendent.
- Invia riepilogo solo all'agronomo.
- Scrive su fogli test.
- Confronta rischio v5.1 vs v5.2.

Obiettivo: rilevare differenze anomale senza impattare gli utenti.

### Fase 3 - Pilota su un campo

Passare un solo campo alla nuova pagina:

- Link v5.2 personalizzato con token campo.
- Vecchio link ancora disponibile.
- Controllo manuale dei primi salvataggi.
- Verifica che email, storico e registro siano coerenti.

### Fase 4 - Migrazione graduale

Se il pilota e stabile:

1. Migrare altri 1-2 campi.
2. Monitorare per errori e feedback.
3. Migrare i campi rimanenti.
4. Solo alla fine dismettere o archiviare la v5.1.

## Criteri di promozione a produzione

La v5.2 puo diventare produzione quando:

- Nessun errore critico nei log per piu cicli di alert.
- Salvataggi `azoto`, `ferro`, `fungo`, `rullatura`, `annotazione` verificati.
- Token campo validati.
- Nessun campo puo scrivere dati su un altro campo.
- Meteo fallback testato.
- Email di alert e riepilogo corrette.
- Rollback verificato.

## Rollback

In caso di problema:

1. Re-inviare ai superintendent il vecchio link v5.1.
2. Disattivare trigger v5.2.
3. Lasciare intatti fogli e dati v5.2 per analisi.
4. Ripristinare solo dopo aver identificato la causa.

## Nota commerciale

Per un abbonamento annuale, il valore percepito dipende piu dall'affidabilita del flusso operativo che dalla sola formula agronomica. Il rilascio progressivo serve a proteggere fiducia e continuita del servizio.
